# repo-scout v1 — план

Цель: перед тем как писать своё, быстро найти на GitHub готовое или близкое решение, которое можно взять за основу, включая свежие проекты с малым числом звёзд. Скрипт работает без генеративных LLM; генерация (Описание задачи, Запросы, Осмотр) остаётся агенту в скилле.

Опоры:
- Термины: `CONTEXT.md`. Методичка: `docs/repo-triage.md` (после Фазы 1).
- Решения: `docs/adr/`. Разбор аналогов: `docs/analogs/README.md` (DeepGit, repohunt, hidden-gems, github-discovery, git-crawler). Синтаксис и лимиты поиска: `docs/search-advices.md`.
- Клоны аналогов: `external_examples/` (в `.gitignore`).

## Конвейер v1

```
скилл: задача → Описание задачи (англ.) + 3–6 Запросов + Жёсткие условия
  → поиск (GraphQL) ─┐
  → Индекс (Близость)┴→ Пул → стоп-правила → Шум → --lang/--exclude
  → пакет README + 20 коммитов → содержательные коммиты → свежесть/«мёртвый» → --must
  → Близость (порог, ключ 1) + баллы методички (ключ 2)
  → второй круг по topics (один раз) → таблица / --json  + запись в Индекс
```

## Фаза 1 — пакет и перенос

- [ ] `pyproject.toml` (uv, Python ≥3.11), пакет `repo_scout/`: `github.py` (GraphQL, rate limit), `triage.py` (стоп-правила, флаги, баллы), `cli.py`; точка входа `repo-scout`.
- [ ] Перенести `scout.py` в модули без изменения поведения; `test_scout.py` → `tests/test_triage.py` (pytest).
- [ ] `uv tool install --editable .`; скилл зовёт `repo-scout` вместо `scout.py`.
- [ ] Перенести `~/dev/docs/repo-triage.md` → `docs/repo-triage.md`, на старом месте симлинк.
- [ ] Поправки поиска из `docs/search-advices.md`: `in:name,description,topics,readme`, `mirror:false`, `--lang` → `language:` в Запросе; проверка лимитов (256 символов текста, ≤5 AND/OR/NOT) до отправки, понятная ошибка.
- [ ] В каждом GraphQL-запросе `rateLimit{cost remaining resetAt}`; ретраи 403/429/«200 без JSON» с backoff (DeepGit `graphql.py:177-209`), 403 считать лимитом только при remaining==0 / Retry-After (repohunt `github.ts:150-160`).

Готово: `repo-scout "q1" "q2"` даёт ту же таблицу, что старый `scout.py`, плюс находит репо, у которых совпадение только в README; тесты зелёные.

## Фаза 2 — Золотые наборы и eval

- [ ] Формат `eval/<набор>.toml`: Описание задачи, Запросы, Жёсткие условия, ожидаемые репо с Вердиктами, дата.
- [ ] Наборы (агент восстанавливает Описание задачи из README/CLAUDE.md проекта, пользователь проверяет):
  linux-coding (`docs/research/opensource-analogs.md` + `analogs/`), buy-smarter, persona-crm, tiktok-lazy-follower, get_cool_event, finance-insights (клон без разбора = «→ Разбор»), repo-scout (`docs/analogs/README.md`).
- [ ] Снимок ответов GitHub: `--record` пишет ответы GraphQL в `eval/snapshots/<набор>/`, `--replay` читает их без сети.
- [ ] `repo-scout eval eval/<набор>.toml`: полнота по «→ Осмотр/Разбор» (сколько в выдаче, на каких местах), ложные отсевы (кем отсеян: стоп-правило / Шум / условие / порог), сколько «отсев» прошло. Сводка по всем наборам одной таблицей.
- [ ] Зафиксировать baseline по текущему конвейеру в `eval/BASELINE.md`.

Готово: eval по всем наборам работает офлайн, baseline записан. Дальше каждая фаза сравнивается с ним; потеря «→ Разбор» = регрессия.

## Фаза 3 — Шум, Жёсткие условия, содержательные коммиты

- [ ] Шум: awesome / tutorial / demo / homework / spam по имени, описанию, topics; отсев только при ≥2 независимых сигналах, причина в выводе. Основа — `external_examples/github-hidden-gems/src/hidden_gems/filtering/rules.py:200-576`. Шаблон — флаг «шаблон», не Шум.
- [ ] Жёсткие условия: `--lang` (primaryLanguage), `--exclude` (регэксп → отсев), `--must` (группы регэкспов по README+topics; README нет → флаг, не отсев). Отсеянные по `--must` — отдельной строкой в выводе.
- [ ] Пакетный GraphQL для выживших (алиасы `r1: repository(...)`, 20–50 за запрос): README (алиасы README.md/readme.md/README.rst…), `history(first:20){committedDate message additions deletions author{user{login}}}`.
- [ ] Содержательный коммит: не служебный бот (dependabot, renovate, github-actions, pre-commit-ci, allcontributors, imgbot, semantic-release-bot) и не косметика (сообщение `docs:|chore(deps)|ci:|style:|bump|release|typo|readme|merge` или крошечная правка текста). Коммиты AI-агентов — обычные. Идеи: `github-hidden-gems/.../light_analysis/activity.py:26-177`.
- [ ] Свежесть и «мёртвый» пересчитываются по последнему содержательному коммиту; нет ни одного среди 20 → дата самого старого + флаг «только косметика».

Готово: тесты на правила Шума, условий и коммитов; eval: Шум из прошлых прогонов (awesome-листы) ушёл, «→ Разбор» не потеряны.

## Фаза 4 — Близость

- [ ] `semantic.py`: fastembed `BAAI/bge-small-en-v1.5`, запрос через `query_embed()`; текст кандидата `name + description + topics + README`, README почищен (бейджи, картинки, layout-HTML; по `external_examples/repohunt/src/readme.ts:1-83`) и обрезан до ~512 токенов.
- [ ] `--task "<Описание задачи>"` обязателен; Близость — первый ключ сортировки, баллы методички — второй; ниже порога — стоп-правило «не по теме».
- [ ] Порог подобрать на eval: максимальный, при котором ни один «→ Разбор» не отсеян. Записать значение и обоснование в `eval/BASELINE.md`.
- [ ] Обновить `docs/repo-triage.md`: Близость (порог + ключ), Жёсткие условия, Шум, содержательные коммиты, новая строка-сводка.

Готово: eval — полнота не хуже baseline, позиции «→ Разбор» выше; пример с разными формулировками одной задачи даёт близкий топ.

## Фаза 5 — Индекс и Вердикты

- [ ] stdlib `sqlite3` (`~/.local/share/repo-scout/index.db`): метаданные, README, `fetched_at`, вектор BLOB float32, имя модели. Перебор косинуса в numpy (ADR-0001; `ponytail:`-комментарий с порогом перехода на sqlite-vec).
- [ ] Запись: каждый кандидат, прошедший стоп-правила и получивший README. Upsert по `owner/name`.
- [ ] Чтение: топ-N по Близости из Индекса добавляется в Пул; их метрики обновляются пакетным GraphQL перед Отсевом.
- [ ] Смена модели → пересчёт векторов из сохранённого README без API.
- [ ] Вердикты: `repo-scout verdict owner/repo "<вердикт>" --project <имя> --task "<кратко>"`; в выдаче колонка «уже смотрели» (проект, дата, вердикт). Никого не скрывает. Скилл вызывает после Осмотра/Разбора.
- [ ] `repo-scout eval --export-verdicts` — Вердикты из Индекса как кандидаты в Золотые наборы.

Готово: повторный поиск соседней формулировкой поднимает репо из прошлого поиска, которых нет в живой выдаче; Вердикт виден во второй сессии.

## Фаза 6 — второй круг

- [ ] Из топ-K (по умолчанию 10) после Близости собрать частые `topics`, исключив уже использованные; до 5 Запросов `topic:<slug>` (+ `language:` при `--lang`), один круг.
- [ ] Новые кандидаты проходят тот же конвейер; в выводе колонка «источник» (запрос / второй круг / Индекс).
- [ ] Обновить скилл: порядок работы, `--task`, условия, `verdict`.

Готово: eval — полнота выросла или не изменилась при ограниченном росте вызовов API (записать оба числа).

## Бэклог (включать только по данным eval)

1. Канал: один шаг от лучших — репо того же владельца и GitHub-ссылки из README (`github-hidden-gems/.../relationships/explorer.py:26-175`).
2. Канал: awesome-листы — `topic:awesome-{слово}` + ссылки из их README (`github-discovery/.../curated_channel.py`).
3. Канал: Sourcegraph `/.api/search/stream` `type:repo` (без токена; поиск по коду там ненадёжен).
4. Канал: реестры PyPI / npm / crates → GitHub.
5. Пути файлов в коммитах (код или документация) для топа — если сообщение и размер ошибаются.
6. Качество по дереву файлов (tests, CI, manifest) и метрики поддержки (bus factor, issues) как третий ключ — `classification.py:139-204`, `maintenance.py:25-190`.
7. Индекс на sqlite-vec / LanceDB — по условиям ADR-0001.
8. OpenSpec — если проект разрастётся.
